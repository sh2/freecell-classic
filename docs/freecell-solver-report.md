# フリーセルソルバー実装レポート

> 対応状況: 2026-08-16 に実装済み。`npm test`(単体 126 / E2E 62)が
> すべて成功。変更の要約は [CHANGELOG.md](../CHANGELOG.md) を参照。

## 概要

- Microsoft FreeCell 互換のフリーセル(クラシックルール)に対して、
  現在の盤面から「勝ち手順(移動のリスト)」を探索するソルバーを追加した。
- 実装形態はユーザー要件に基づく 3 点:
  1. ブラウザ組み込み(ツールバーの「ヒント」「自動解答」ボタン)。
  2. 出力は勝ち手順の列(移動のリスト)。
  3. ビットボード等の最適化を意識した高速寄りの実装。
- 探索は Web Worker 上で実行し、画面をブロックしない。

## 目的と要件

- 現状の盤面からゲームを解き、クリアまでの手順を提示する。
- 「ヒント」は手順を表示するだけ(盤面を進めない)。
- 「自動解答」は手順を 1 手ずつ再生してクリアまで進める。
- 探索は必ず終了する(ノード数・時間の上限で打ち切る)。
- 探索コアは DOM に依存しない純粋関数とし、単体テスト可能にする。

### 盤面の表現

- カードは id(0〜51)で表す。既存のディールと同じ規則:
  - `suit = id % 4`(0=♣, 1=♦, 2=♥, 3=♠)
  - `rank = Math.floor(id / 4) + 1`(ビット演算では `id >> 2` と `id & 3`)
  - 赤は `suit === 1 || suit === 2`
- 探索中の状態は 1 つの可変状態を使い回す(make/unmake 方式):
  - `cols`: 8 列。各列はカード id の配列(最大長 19 を想定)。
  - `free`: `Int8Array(4)`。空きは `-1`。
  - `found`: `Int8Array(4)`。各スートの土台先頭ランク(0=空)。
  - `totalHome` / `totalCards`: 勝利判定とヒューリスティック用の枚数。
    `totalCards` を動的に数えるため、52 枚に満たない部分盤面も解ける。

## アルゴリズム

### 全体: IDA\*(反復深化 A\*)

- 反復深化 DFS にヒューリスティック下限 `h` を組み合わせ、
  `f = g + h` が閾値を超えた枝を刈りながら、閾値を徐々に上げて再探索する。
- メモリは「現在の経路」+「置換表」だけで済み、A\* のような
  オープンリストの爆発がない。

### 自動ホーム(土台への移動の扱い)

- FreeCell では土台(foundation)へ置いたカードは戻せず、土台への移動は
  常に安全。したがってホームへの移動を「分岐」にせず、決定的な
  「自動ホーム」として可能な限り即適用する。
- これにより状態空間が大幅に削減され、探索の各ノードは常に
  「ホームへ送れるカードが 1 枚もない正規化済み状態」になる。

### 手の生成

- ホームへの移動を除いた分岐手のみを列挙する:
  1. 列 → 列(スーパームーブ含む)。各列について、先頭から連続する
     降順・色交互の連続列(末尾)をすべて試し、置ける列へ移動する。
     移動可能枚数は既存ルールと同じ `(空きフリーセル+1) * 2^空き列`。
  2. 列 → フリーセル。
  3. フリーセル → 列。
- フリーセル → フリーセルは無意味なシャッフルなので生成しない。

### ヒューリスティック

```text
h = (残りカード数)
  + Σ 各列の「可動末尾より下にあるカード数」
```

- 残りカード数は、どの非ホームカードも最低 1 回は土台へ動かす必要がある
  という下界。
- 「可動末尾」とは、列の先頭からスーパームーブでまとめて動かせる連続列。
  その下のカードは上を退けるまで動かせないため 1 手分を加算する。
- 後半の加算は厳密には過大評価になり得る(非許容的)が、本実装は最短解を
  求めず「解を 1 つ見つける」ことが目的のため許容する。実際、
  過大評価により閾値が速く上がり、実ゲームの探索ノード数が大幅に減少した。

### 置換表と Zobrist ハッシュ

- 同一状態の再探索を防ぐため、64bit(32bit × 2)の Zobrist ハッシュで
  状態を識別する置換表を用いる。
  - 鍵は `列(col, pos, card)`・`土台(suit, rank)`・`フリーセル(card)`
    に乱数を割り当て、make/unmake 時に XOR で増分更新する。
  - フリーセルは「どの空きマスか」を区別せず、置かれたカードだけで
    ハッシュする(フリーセルは対称なので正規化になる)。
- 置換表はオープンアドレス法 + 線形探索(容量 2^21 スロット)。
  同じ鍵には最小の `g` を保持し、`g` が既知値以上なら枝を刈る。

### 枝刈りと探索打ち切り

- 直前の分岐手の「逆手」を生成しない(無意味な往復の抑制)。
- 置換表の最小 `g` 枝刈りは「同一イテレーション内でのみ」正しいため、
  IDA\* の閾値を上げるたびに置換表をクリアする。これを怠ると、低い閾値で
  浅く刈った状態が高い閾値でも再展開されず、解を取りこぼす。
- `maxNodes`(既定 2,000,000)/ `maxTimeMs`(既定 60,000)で打ち切り、
  `node-limit` / `time-limit` を返す。打ち切りは例外で探索を即座に脱出する。
- 勝利を検出した時点で `path` の複製を `solutionMoves` に保存する。
  (DFS の巻き戻しで `path` が pop されるため、後から参照すると壊れる)

## UI / Worker 統合

- `solver-client.js` が Worker の生成・破棄を管理し、結果受信後に
  `view.showSolution()` で解答手順パネルを表示する。
- 「自動解答」は受信後に `app.applyMoveInstant()` で 1 手ずつ再生する。
  自動ホームは順序を保つため一時的に無効化し、終了後に戻す。
- 計算中はボタンを無効化し「計算中…」と表示する。
- 新しいゲームを開始したら古い解答パネルを閉じる。

## テスト

### 単体テスト(`tests/unit/solver.test.js`)

- 勝利済み盤面(0 手)、あと 1 手の盤面(1 手)、A 4 枚(4 手)、
  退避が必要な盤面(7 手)、解けない盤面(上限到達)、決定的再現性、
  `cardName` / `formatMove` などを検証。
- 各テストは、得られた手順をゲーム本体の `attemptMove` で再生し、
  実際に全カードがホームへ揃うことまで確認する。

### E2E テスト(`tests/e2e/freecell.spec.js`)

- 「ヒント」で解答手順パネルが表示され、盤面が進まないこと。
- 「自動解答」で勝利オーバーレイが表示され、`won` になること。
- 解答パネルが閉じるボタンで閉じること。

## 性能評価

手元環境での参考値(Worker ではなく `solver.js` を直接呼んだ測定)。

| 対象 | 結果 | ノード数 | 時間 | 備考 |
| --- | --- | --- | --- | --- |
| Game #1 | solved(96 手) | 約 13,554 | 約 40ms | 手順を再生して勝利確認済み |
| Game #12 | node-limit | 2,000,000 | 約 1.8s | 難しめの配布 |
| Game #11982 | node-limit | 2,000,000 | 約 1.5s | 既知の「解なし」配布 |

- Game #1 は手順 96 手をゲーム本体の `attemptMove` で再生し、
  `isWon()` が true になることを確認した(探索と既存ルールの整合性を検証)。
- 解けない配布(#11982)は誤って「解けた」とはせず、上限到達として
  正しく打ち切る。

## 制限と今後の課題

- 現在のヒューリスティックでは、簡単〜中程度の配布は解けるが、
  難しい配布(例: Game #12)は既定上限内で解けない。
- 全 32,000 配布を安定して解くには以下が必要:
  - より強いヒューリスティック(Deadlock 検出、空き列の価値評価など)。
  - 列の対称性の正規化(置換表ヒット率の向上)。
  - より大きなノード/時間上限、または反復ごとの改善。
- 「解けない」ことの完全な証明は行わない。あくまで上限到達として報告する。
