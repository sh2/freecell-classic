# ソルバー改善計画 (fc-solve との比較に基づく)

> 対象: `src/js/solver.js` の探索エンジン。
> Shlomi Fish 氏の fc-solve との比較調査から、実装規模が小さく効果が大きい
> 改善に絞ってピックアップする方針とする。

## 背景と目的

- 現状のソルバーは「IDA\* + 自動ホーム + Zobrist ハッシュの置換表」で、
  Game #1 は約 1.3 万ノード / 約 40ms で解ける。
- 一方、Game #12 はノード上限 (2,000,000) に達して解けない
  (`node-limit` を返す)。
- 同盤面を fc-solve は即座に解くため、その差を調査し、本プロジェクトへ
  取り込むべき改善を絞り込む。

## 1. fc-solve 調査結果 (要点)

### 1.1 fc-solve とは

- Shlomi Fish 氏が開発する C 製のフリーセル自動解答プログラム。
  20 年以上の改良を経て、Microsoft の全 32,000 配布のうち #11982 以外を
  解ける (Web 版は WebAssembly で動作)。
- 探索は「1 つの万能アルゴリズム」ではなく、複数のスキャン
  (soft-thread / flare) を切り替えて動かす設計。

### 1.2 高速化の主要因

1. **列の正規化 (Canonicalization)**
   8 本の列の並び順を無視して同一局面をまとめる (列の対称性の排除)。
2. **Meta-Moves**
   目的駆動の複合手で探索木を浅くする。
3. **探索戦略**
   Soft-DFS や多重スキャンで、手の試行順を局面に応じて変える。
4. **Horne's Rule などの枝刈り**
   将来の受け皿を潰さない「安全な土台送り」。
5. **C / WebAssembly と極小状態表現**
   状態 1 つを数十バイトに圧縮し、キャッシュヒット率を最大化。

## 2. 本ソルバーとの比較

| 項目 | 本ソルバー (`src/js/solver.js`) | fc-solve |
| --- | --- | --- |
| 探索 | IDA\* (反復深化 A\*) | Soft-DFS / 多重スキャン (flare) |
| 列の正規化 | なし (フリーセルのみ) | あり (列を正規化して対称性排除) |
| 手の生成 | 基本手 + スーパームーブ | Meta-Moves (複合手) |
| 土台送り | 無条件の自動ホーム | Horne's Rule による安全な土台送り |
| 実装基盤 | 純 JS (Web Worker) | C → WebAssembly |

## 4. 採用する改善

### 4.1 列の正規化 (最優先)

#### 現状

- Zobrist ハッシュの鍵は `zColIndex(col, pos, card)` で、**列の位置 (col) を
  含む**。
- このため「列 A と列 B を入れ替えただけの同一局面」が別ハッシュになり、
  置換表が効かず重複探索される。最悪 $8! = 40{,}320$ 通りの同一局面が
  生じ得る。
- フリーセルは既に「どの空きマスか」を区別せず正規化済み。土台はスート固定で
  正規化済み。未対応なのは列のみ。

#### 変更内容

列ハッシュを「列の位置に依存しない」形へ変更する。

- 鍵から col 次元を外す: `zColIndex(pos, card) = pos * 52 + card`。
- 各列のハッシュは列内の位置 `pos` だけで決まり、全列のハッシュを XOR する。
  XOR は可換・結合的なので、列の並び順を変えても合計ハッシュは同じになる。
- `COL_SIZE` を `NUM_CASCADES * MAX_COL_LEN * 52` → `MAX_COL_LEN * 52` に変更。
- `xorCol(col, pos, card)` → `xorCol(pos, card)` とし、呼び出し箇所 (約 10 箇所)
  から列インデックス引数を外す機械的変更。

```js
// 変更前
const zColIndex = (col, pos, card) => col * (MAX_COL_LEN * 52) + pos * 52 + card;
// 変更後
const zColIndex = (pos, card) => pos * 52 + card;
```

#### 正しさの注意

- 空列はハッシュに寄与しない (カード 0 枚 = XOR 0)。カードは盤面に 1 枚しか
  無いため、非空列の列シーケンスはすべて相異なる。よって XOR の打ち消しは
  空列同士でのみ起こり得るが、空列の本数は「8 − 非空列の本数」で一意に
  決まるため、状態の区別を損なわない。
- ハッシュ衝突 (異なる状態が同一ハッシュになる) は64bit Zobristの実用上十分
  低い確率として許容する。`unsolvable` はこの衝突が発生していないという仮定
  付きの結果であり、数学的な完全証明ではない。

#### 期待効果

- 置換表のヒット率が大幅に向上し、探索ノード数が桁で減る。
- Game #12 が既定上限内で解けるようになる見込み (要検証)。

### 4.2 手の試行順 (move ordering) の改善

#### 現状

`moveScore()` が静的スコアで手をソートしている
(列移動: 枚数×10000 + 非空列へ +5000 + 元列が空に +3000、フリー移動: 2000 +
元列が空に +3000)。「その手の後に何枚自動ホームできるか」は見ていない。

#### 変更内容 (小)

- 列移動で「移動後に露出するカード」が自動ホーム対象 (土台へ送れる) になる
  場合にスコアを加点する。`generateMoves()` 内は `cols` が見えるため、
  移動元の残りの先頭カードが `found` と合致するかを確認するだけで済む。
- 空列を作る手の重みを引き上げる (現行の +3000 は控えめ)。

#### 期待効果

IDA\* は正しい順で手を試すほど早く解に到達する。自動ホーム連鎖につながる手を
先に試すことで、解までのノード数を削減する。

### 4.3 空列への重複手の排除

#### 現状

列 → 空列、フリーセル → 空列の移動で、**空列ごとに**移動手を生成している。

#### 変更内容 (極小)

列正規化後はどの空列へ動かしても同一状態になるため、空列の移動先は 1 つ
(先頭の空列) だけに絞ってよい。生成手数を減らせる。

### 4.4 置換表容量・上限の調整

- `createTranspositionTable(capacityBits = 22)` (2^22 = 約 419 万スロット)。
  列正規化でヒット率が上がると、容量不足による上書きが増える可能性がある。
  メモリに余裕があれば 22〜23 へ引き上げる。
- `maxNodes` (既定 2,000,000) / `maxTimeMs` (既定 60,000) は、ゲーム UI の
  体感 (数秒以内が望ましい) と相談して調整する。

## 5. 見送り / 要調査

- **Horne's Rule (要調査)**
  本ソルバーは「土台送りは常に安全」と仮定して無条件の自動ホームを行っている。
  しかし一般には、土台へ送ったカードが、より低ランクの逆色カードの受け皿
  として後で必要になる場合がある。難しい配布で解けない一因になっている
  可能性があり、既知のハード配布で検証する価値がある。ただし変更は正しさに
  関わるため、まず列正規化の効果を見てから判断する。
- **Deadlock 検出 (見送り)**
  効果は中程度だが、実装と検証のコストが大きい。
- **Soft-DFS / 多重スキャン (見送り)**
  効果は大きいが探索エンジンの再実装に近く、本計画のスコープ外。列正規化 +
  手順改善で足りない場合の次段階とする。
- **Meta-Moves (見送り)**
  効果は大きいが、手の生成・再生 (`applyMoveInstant`) との整合など影響範囲が
  広い。
- **WebAssembly 化 (見送り)**
  「依存ライブラリなし・ビルドなし」の設計方針に反するため見送る。

## 8. 実装結果と性能評価 (2026-08-16)

4 章の「採用」4 項目を実装した。変更の要約は [CHANGELOG.md](../CHANGELOG.md)
を参照。

### 8.1 実装内容

| 項目 | 実装の要点 |
| --- | --- |
| 4.1 列の正規化 | `zColIndex(pos, card)` に変更し、全列のハッシュを XOR 合成。同一局面を同一ハッシュに帰着 |
| 4.2 手の試行順 | 露出カードが自動ホーム対象になる手に +15000、空列を作る手を +3000 → +20000 に引き上げ |
| 4.3 空列の重複排除 | 列→列・フリーセル→列の移動先を先頭の空列 1 つに正規化 |
| 4.4 置換表容量 | 2^21 → 2^22 スロットに引き上げ |

### 8.2 性能評価

計測は `src/js/solver.js` を直接 import する Node スクリプトで行った
(既定上限: 200 万ノード / 60 秒)。

| 対象 | 変更前 | 変更後 |
| --- | --- | --- |
| Game #1 | solved (約 13,554 ノード / 40ms) | solved (13,735 ノード / 51ms) |
| Game #12 | node-limit (200 万ノード) | **solved (71,698 ノード / 136ms)** |
| Game #11982 | node-limit (200 万ノード) | node-limit (200 万ノード) |

- 列の正規化が主因で、Game #12 が「解けない」から約 7.2 万ノードで解ける
  ようになった (解は 94 手。Game #1 は 96 手のまま)。
- Game #11982 は既知の「解なし」配布で、誤って「解けた」とはせず上限到達の
  まま正しく打ち切る。

### 8.3 挙動の変化

- 状態空間が縮小したことで、解けないことを証明できる小さな盤面は
  `node-limit` ではなく `unsolvable`(全状態を探索し尽くした判定)を返すように
  なった。`tests/unit/solver.test.js` の該当テストを追従更新した。
- `npm test` (単体 126 / E2E 62) がすべて成功することを確認済み。
